# Объединённый backend

Ветка `codex/team-integration` сохраняет транзакционные RPC, Academy, приглашения,
делегирование и HR обращения из `test`; роли директора, администрирование ролей,
личный кабинет и окончательное списание отпуска из `main`; Jana и `.ics` из `Integration`.
Общая Supabase при сборке не изменялась.

## Заявки и баланс

- `pending`: назначенный руководитель или директор рассматривает заявку. Состав
  согласующих фиксируется при отправке. Изменение руководителя не выдаёт доступ
  к чужим старым заявкам. Допускается действующее явно назначенное замещение.
  Замещать первый этап могут только руководители и директора; HR создаёт
  замещение и сохраняет право окончательного решения. В отличие от прежней
  одноэтапной ветки `test`, роль HR не назначается заместителем первого этапа.
- Согласование руководителем переводит заявку в `pending_hr`. HR не может
  пропустить этот этап. Если подходящего руководителя нет, заявка направляется
  непосредственно HR. Никто не может согласовать собственную заявку.
- HR принимает окончательное `approved`/`rejected`. Отклонение требует причины.
  Комментарии и авторы первого и последнего этапов сохраняются отдельно.
- Владелец может отменить `pending` и `pending_hr`. Окончательно одобренную заявку
  отменить этим API нельзя; автоматического возврата списанных дней нет.
- Отпуск считается в календарных днях, включая обе границы. Начало в прошлом,
  пересечения с `pending`/`pending_hr`/`approved`, сумма в отпускной заявке и
  резерв сверх доступного остатка отклоняются.
- При отправке дни резервируются. На `pending_hr` резерв сохраняется. Только
  окончательное одобрение HR уменьшает `vacation_days_remaining`, а резерв
  становится `reconciled`: повторного вычета из доступного остатка нет.
- Изменение статуса, история, уведомления, резерв, списание и записи outbox
  выполняются в одной транзакции. Идентичные повторы безопасны, включая
  одновременное окончательное согласование.
- `/workspace/leave-balance` сохраняет поля `official_days`, `pending_days`,
  `approved_unreconciled_days`, `available_days`, `holds`. Новые одобренные
  отпуска не попадают в `approved_unreconciled_days`; поле оставлено для
  явно сверяемых исторических резервов. HR сверка не может опустить остаток
  ниже ещё действующих резервов.
- `.ics` доступен только после окончательного одобрения. Доступ к файлу тот же,
  что к карточке заявки. Google Calendar импортирует файл вручную; синхронизации нет.

`pending_director` сохранён только как прежнее значение enum. Новый маршрут
не создаёт отдельную стадию директора: директор рассматривает заявки своих
непосредственных подчинённых на первом этапе.

## Остальные контракты

`GET /profile` возвращает `manager_name` для интерфейса `test`, а также
`manager`, `assigned_courses`, `notifications` из `main`. Официальные сведения
не редактируются сотрудником. HR меняет роли через `/admin/employees/{id}/role`;
редактирования `manager_id` этим endpoint нет. В запросах используется роль
из профиля, а не роль, переданная браузером.

Регистрация требует приглашения HR и подтверждения email. Только после этого
создаётся профиль с данными и ролью из приглашения. Поддержаны директор в
качестве руководителя и роль директора в приглашении.

Academy сохраняет назначение, версии материалов, уроки, сроки и попытки.
После материала необходимо набрать проходной балл курса; только тогда статус
`completed` и прогресс 100%. Неуспешный тест можно повторить. Директор, как
руководитель, управляет обучением непосредственных подчинённых.

HR обращения создаются отдельным endpoint только при `consent: true`. Ответ
Jana сам по себе не отправляет обращение. Outbox для 1С/Documentolog означает
очередь доставки; без настроенного внешнего сервиса это не готовая интеграция.

## Миграции и проверка

Единственный полный порядок для **новой локальной тестовой БД** находится в
[`database/migration-plan.json`](../database/migration-plan.json). Исходные
миграции `test` оставлены в `database/migrations`; исторические миграции `main`
в `database/migrations/main`; `0011_team_workflow.sql` согласует их поведение.
Не применять этот bootstrap к общей Supabase: сначала необходима отдельная
инвентаризация её истории, данных и остатков.

[`scripts/check_team_database.py`](../scripts/check_team_database.py) принимает
только явный loopback DSN к пустой `posttech_test_*` БД, создаёт свою временную
БД, применяет весь план и удаляет только созданную им копию. `.env` не читается.

Новые тесты `test_team_workflow_db.py` и `test_team_http_db.py` проверяют полный
план и объединённые правила. Старые DB-тесты дополнительно проверяют исторические
стадии миграций; их прежнее ожидание «остаток не списывается» относится только
к этим стадиям, а не к текущей системе. Исторический seed вынесен в
`tests/fixtures/test_branch_seed.sql`; актуальный `database/seed.sql` использует
тот же маршрут согласования, что HTTP API.
