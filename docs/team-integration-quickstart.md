# Запуск Integration с общим Supabase и локальной Jana

Эта инструкция для команды PostTech: запускаем фронтенд и API на своём
компьютере, входим через общий Supabase и проверяем Jana на общей базе знаний.
Основной вариант — Windows и PowerShell. Docker, видеокарта и ключ OpenAI
для него не нужны.

Связь компонентов: браузер → фронтенд на `127.0.0.1:5173` → API на
`127.0.0.1:8000` → Supabase. Поиск ответа Jana выполняется на CPU вашего
компьютера. Интернет нужен для входа, статей и заявок в Supabase.

## Что подготовить

- Git, Python **3.12 x64** и Node.js **22.x** с npm. Эти версии соответствуют
  окружению проекта; основной вариант рассчитан на Windows x64.
- Доступ к репозиторию [Dmitribear/PostTech](https://github.com/Dmitribear/PostTech).
- Доступ к [общему проекту Supabase](https://supabase.com/dashboard/project/zcsoipcwymhowmvnytxf)
  или нужные настройки от участника команды с доступом к серверу.
- Два тестовых входа в портал: сотрудник и его непосредственный руководитель.
  Запросите их у автора ветки Integration отдельно. У него они сохранены в
  локальном `.venv/supabase-integration-accounts.json`; в Git этого файла нет.
  Учётная запись панели Supabase и учётная запись нашего портала — разные входы.

**Общий Supabase уже подготовлен.** Для подключения не запускайте миграции,
`seed.sql`, `seed_jana_demo.sql` или сброс базы. Ветки `test` и `ver2` содержат
разные варианты миграций, поэтому применять их поверх общей базы без согласования
нельзя. Тестовые заявки здесь сохраняются и видны участникам команды.

## Получить ветку

Откройте PowerShell в папке, где храните проекты, и выполните:

```powershell
git clone --branch Integration --single-branch https://github.com/Dmitribear/PostTech.git PostTech-Integration
cd PostTech-Integration
git branch --show-current
```

Последняя команда должна показать `Integration`. Отдельная папка позволит
сохранить вашу текущую работу во фронтендовой или бэкендовой ветке.
Дальше «корень проекта» означает эту папку, где находятся `app`, `frontend`
и `.env.example`.

## Подключить общий Supabase

Из корня проекта создайте файл настроек, сохранив существующий, если он уже есть:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
notepad .env
```

Откройте [Settings → API Keys общего проекта](https://supabase.com/dashboard/project/zcsoipcwymhowmvnytxf/settings/api-keys).
Скопируйте существующие ключи и замените значения в трёх строках `.env`:

```dotenv
SUPABASE_URL=https://zcsoipcwymhowmvnytxf.supabase.co
SUPABASE_KEY=sb_secret_ЗАМЕНИТЕ_НА_ПОЛНЫЙ_СЕРВЕРНЫЙ_КЛЮЧ
SUPABASE_ANON_KEY=sb_publishable_ЗАМЕНИТЕ_НА_ПОЛНЫЙ_ПУБЛИЧНЫЙ_КЛЮЧ
```

Это шаблон: вставьте полные значения без многоточий и переносов внутри ключа.
Названия переменных оставьте именно такими: историческое имя
`SUPABASE_ANON_KEY` в нашем коде используется и для нового publishable key.
Остальные настройки из `.env.example` оставьте как есть; `OPENAI_API_KEY`
может быть пустым. Сохраните файл как `.env`, без расширения `.txt`.

Серверный secret key даёт расширенный доступ к базе. Храните его только в
корневом `.env` своего бэкенда; не помещайте в `frontend`, переменные `VITE_*`,
коммиты или скриншоты. Типы ключей описаны в
[документации Supabase](https://supabase.com/docs/guides/getting-started/api-keys).
Для обычного запуска создавать или перевыпускать ключи не требуется.

## Установить Python зависимости и модель

В корне проекта:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m scripts.prepare_jana_local
```

Ожидаемый результат последней команды — `Local model ready: ...`.
При первом запуске загружается около 288 МБ в `.models/mpnet`; скрипт проверяет
контрольные суммы. Модель и виртуальное окружение не скачиваются из Git,
поэтому этот шаг нужен на каждом компьютере. Повторный запуск использует
уже загруженные корректные файлы.

Активация окружения не нужна: команды явно используют его Python. Если
`py` не найден, установите Python 3.12 или используйте `python -m venv .venv`,
предварительно убедившись через `python --version`, что это версия 3.12.
Путь `.venv\runtime\Scripts\python.exe` из заметок об авторском компьютере
не относится к этому новому окружению.

## Запустить API и фронтенд

**Первый терминал**, корень проекта:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

Оставьте терминал открытым. В браузере проверьте
[API health](http://127.0.0.1:8000/api/v1/health/live): ожидается
`{"status":"alive"}`. [Swagger](http://127.0.0.1:8000/docs) показывает маршруты
API. Health подтверждает работу процесса; доступ к настоящей базе проверим входом.

**Второй терминал**, сначала перейдите в корень того же проекта, затем:

```powershell
cd frontend
npm.cmd ci
npm.cmd run dev
```

Откройте [портал](http://127.0.0.1:5173). Команда `npm.cmd` в PowerShell
позволяет запускать npm без изменения политики выполнения скриптов.
При последующих запусках достаточно `npm.cmd run dev`; повторный `npm.cmd ci`
нужен после изменения зависимостей.

Фронтенд уже перенаправляет `/api` на `http://127.0.0.1:8000`. Для этого
варианта настройки `frontend/.env.local` не нужны. Если файл остался от прежних
экспериментов, проверьте `API_PROXY_TARGET` и уберите переопределение
`VITE_API_BASE_URL`, которое уводит запросы на другой сервер.

Чтобы остановить серверы, нажмите `Ctrl+C` в каждом терминале. После изменения
корневого `.env` перезапустите API; после изменения настроек фронтенда — Vite.

## Проверить Jana через фронтенд

Войдите тестовым сотрудником через **«Войти в систему»**. Кнопка
«Открыть демоверсию» включает отдельный режим с вымышленными данными в браузере
и не проверяет общий Supabase. После обычного входа внизу меню должна быть
надпись **«PostTech API · Подключено»**, без баннера демоверсии.

Откройте **AI Jana** и проверьте:

| Действие | Ожидаемый результат |
| --- | --- |
| Спросить «Хочу уйти в отпуск, как подать заявку?» | Короткий ответ об оформлении отпуска со ссылкой `[1]` и кнопкой источника. |
| Нажать на источник | Открываются дословный фрагмент ответа и полный материал из Supabase. |
| Спросить «Какая погода завтра?» | Отказ: «В базе нет подтверждённого ответа. Уточните у HR.» |
| Спросить «Какой точный размер моей зарплаты?» | Отказ без источников; выдуманной суммы нет. |

Первый ответ может идти дольше из-за загрузки модели и индекса. ИИ подбирает
проверенную FAQ-цитату по смыслу вопроса; платные API для ответов не вызываются.
Статьи пока учебные, поэтому слово «Демо» в названии источника нормально
даже при настоящем подключении к Supabase. Это не утверждённые правила JanaPost.

## Проверить заявку и календарь

1. Под тестовым сотрудником откройте «Мои заявки» и оформите **одну** заявку
   на отпуск с будущими датами. В комментарии напишите
   `ТЕСТ ИНТЕГРАЦИИ — ваше имя — дата проверки — не реальный отпуск`.
   Сохраните номер заявки; ожидаемый статус — на согласовании (`pending`).
2. Выйдите и войдите тестовым руководителем этой пары. Найдите заявку сотрудника
   и одобрите её с тестовым комментарием. Собственные заявки одобрять нельзя.
3. Снова войдите сотрудником. Проверьте статус **«Одобрено»**, запись об одобрении
   в истории и уведомление о решении. После обновления страницы данные должны
   сохраниться.
4. В карточке одобренного отпуска нажмите **«Скачать отпуск (.ics)»**.
   Даты в файле должны соответствовать заявке. Скачивание доступно только для
   одобренного отпуска.
5. Если проверяете импорт, используйте отдельный тестовый Google-календарь:
   на компьютере откройте «Настройки» → «Импорт и экспорт», выберите `.ics`
   и этот календарь. [Инструкция Google](https://support.google.com/calendar/answer/37118?hl=ru).

Импорт выполняется вручную. Перенос или отмена заявки автоматически не меняют
событие в Google Calendar. Одобрение заявки также не списывает баланс дней
и не создаёт документ в 1С или Documentolog.

Для просмотра без новой заявки в тестовом аккаунте уже есть одобренная
`REQ-528486A2` на 10–12 ноября 2026 года. Чтобы руководитель увидел заявку,
у сотрудника в `employee_profiles.manager_id` должен быть ID именно его
HR-профиля. У подготовленной тестовой пары эта связь уже настроена.

## Решение проблем при запуске

| Симптом | Что проверить |
| --- | --- |
| Портал не открывается | Второй терминал работает, Vite запущен на порту 5173. |
| Ошибка подключения к API или `ECONNREFUSED` | Первый терминал работает; health доступен на порту 8000; прокси фронтенда направлен туда же. |
| Порт занят | Остановите свой ранее запущенный экземпляр сервера или согласуйте другие порты и `API_PROXY_TARGET`. |
| Вход возвращает 503 | В корневом `.env` заполнены все три настройки Supabase; ключи не перепутаны; после сохранения API перезапущен. |
| Неверный email или пароль | Используются данные тестового аккаунта портала, а не вход в панель Supabase. |
| «Аккаунт создан, но ещё не связан с HR-профилем» | Администратор должен связать Auth ID с `employee_profiles.auth_user_id`. Одна регистрация не назначает роль. |
| «Локальная Jana сейчас недоступна» или 503 у `/ai/ask` | Успешно завершился `scripts.prepare_jana_local`; API запущен из корня проекта; модель находится в `.models/mpnet`. Причина также видна в терминале API. |
| Известный вопрос получает отказ | Статья активна, её текст и `source_sha256` в FAQ совпадают; при изменении статей или карточек нужна согласованная правка базы знаний. Не загружайте seed поверх общей базы для исправления. |
| Руководитель не видит заявку | Используется соответствующий руководитель, проверяется нужный сотрудник и сняты лишние фильтры списка. |

Вопросы о новой или изменённой базе сначала проверьте read-only скриптом
[`database/check_shared_supabase.sql`](../database/check_shared_supabase.sql)
в SQL Editor. Он показывает структуру и права, ничего не изменяя.
Подробности совместимости — в [документации портала](frontend.md).

## Обновление рабочей копии

Из корня отдельной папки Integration:

```powershell
git status --short
git branch --show-current
```

Если есть ваши изменения, сначала сохраните их в своей рабочей ветке или коммите.
Убедившись, что текущая ветка — `Integration`, обновитесь:

```powershell
git pull --ff-only origin Integration
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m scripts.prepare_jana_local
cd frontend
npm.cmd ci
```

Если Git сообщает о разошедшихся ветках, согласуйте объединение с командой.
Не используйте `reset --hard` для обхода ошибки. После обновления перезапустите
оба сервера.

## Проверки после изменения кода

В корне проекта:

```powershell
.\.venv\Scripts\python.exe -m pytest -q -p no:cacheprovider
.\.venv\Scripts\python.exe -m scripts.check_jana_release --output-dir .venv/jana-check-1
```

В папке `frontend`:

```powershell
npm.cmd test
npm.cmd run build
```

Эти проверки дополняют ручной сценарий выше. Отдельные PostgreSQL-тесты требуют
изолированной тестовой базы; общий Supabase команды для них не используйте.
Не запускайте `scripts.evaluate_jana`: это прежний эксперимент с платным OpenAI.
Полная локальная проверка ИИ называется `scripts.check_jana_release`: девять
наборов, 285 вопросов, без платных вызовов и без Supabase. Выбирайте новую папку
результатов на каждый запуск; код выхода 0 означает полный успешный прогон,
1 — несовпадения ответов, 2 — ошибку или неполный прогон.
Одиночный набор можно проверить через `scripts.evaluate_jana_local`.
Результаты текущей версии и ограничения описаны в [отчёте](jana-release-report.md).
