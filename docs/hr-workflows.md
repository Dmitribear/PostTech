# Пять улучшений HR-процессов

Реализованы 17 октября 2026. Достижения, рейтинги и баллы не добавлялись.

## Приглашения и роли

HR → Сотрудники → Пригласить сотрудника: HR назначает роль, руководителя и кадровые данные. Сотрудник вводит код приглашения, видит назначенную роль, задаёт пароль и подтверждает почту отдельным цифровым кодом Supabase. Клиентские поля `role`, `email` и произвольные метаданные в регистрации отклоняются; профиль создаётся по данным приглашения после подтверждения почты. Вход в тестовые кабинеты вынесен в отдельную демонстрацию, без имитации регистрации.

Миграция `0013_invitation_email.sql` добавляет состояние письма отдельно от состояния активации и отправки Auth-кодов. Письмо через Resend содержит роль, подразделение, код и срок действия. Для сервера нужны `RESEND_API_KEY`, `INVITATION_EMAIL_FROM` (по умолчанию `PostTech <onboarding@resend.dev>`) и, при наличии доступного стенда, `PORTAL_PUBLIC_URL`. SMTP внутри Supabase обслуживает подтверждение и восстановление пароля, но не заменяет ключ отправителя PostTech. После изменения `.env` пересоздайте контейнер: `docker compose up -d api`.

`accepted` означает принятие письма сервисом, а не подтверждённую доставку в ящик. Отказ и неизвестный результат (например, таймаут) отображаются отдельно. Без ключа приглашение сохраняется, но интерфейс прямо сообщает, что письмо не отправлено; код доступен HR для ручной передачи. В списке «Выданные» можно отправить новый код, в том числе для приглашений из импорта. Сам импорт не рассылает письма автоматически.

Повторная отправка доступна не чаще раза в минуту и заменяет предыдущий код. Получатель, роль и срок действия сохраняются; истёкшие, отозванные и использованные приглашения отправлять нельзя. В базе сохраняется только хеш кода; поздний ответ сервиса не перезаписывает состояние новой попытки. Для одной попытки используется [ключ идемпотентности Resend](https://resend.com/changelog/idempotency-keys), исключающий повторную отправку того же запроса. После сбоя процесса HR может повторить отправку из списка; автоматической очереди для этих писем пока нет.

## Согласование и оформление

Статус заявки `approved` означает принятое решение. Отдельная запись `request_fulfillment` показывает `awaiting_hr`, `processing` или `completed`. В списке сотрудник видит «Ожидает HR», «Оформляет HR», «Оформлено». Номер документа и история оформления доступны в карточке. Собственную заявку HR оформлять не может; решение руководителя тоже не снимает это ограничение.

Без внешних систем HR указывает номер **уже оформленного** документа и подтверждает оформление. Когда оба приёмника настроены, появляется передача в 1С и Documentolog. События создаются после явного действия HR, а не сразу после согласования. `delivered` в очереди означает подтверждённый приём события; номер документа всё равно вносится отдельно. Полного обмена документами и проверки подлинности номера пока нет: для этого нужны реальные API приёмников.

Старые согласованные заявки сохранены. Уже существующие события не отправляются повторно при миграции. Если событие ещё ни разу не отправлялось, ручное оформление помечает его `cancelled` с записью в истории. Если отправка хотя бы начиналась, ручное завершение блокируется до подтверждения приёмников: нельзя создавать второй документ при неизвестном результате первой попытки.

Оформление не списывает остаток отпуска повторно. Резерв остаётся до отдельной сверки с кадровым остатком.

## Импорт CSV / XLSX

Один лист, до 500 сотрудников, файл до 2 МБ. Шаблон скачивается на экране импорта. Поддерживаются UTF-8 CSV с запятой/точкой с запятой и Excel. Даты — `ГГГГ-ММ-ДД`; табельные номера в Excel должны быть текстом. Формулы, лишние столбцы, слишком большие архивы и дубли отклоняются.

Обязательные столбцы: `employee_code,full_name,email,company,job_title,department,hired_at`. Дополнительные: `role,manager_email`. Допускаются и соответствующие русские заголовки. `role` по умолчанию `worker`; новый руководитель — `manager`. Массовое создание HR запрещено: такие права выдаются отдельным приглашением. `manager_email` должен принадлежать уже активному руководителю/HR; при пустом значении согласование идёт через HR.

Предпросмотр показывает новые приглашения, неизменившиеся записи, конкретные значения до/после и ошибки по строкам. Если есть ошибка, кнопка применения недоступна. Срок предпросмотра — час. Применение атомарно: если с момента проверки изменился сотрудник или возник конфликт приглашения, весь пакет откатывается. Повтор того же пакета не создаёт новые приглашения.

Существующим сотрудникам меняются только ФИО, компания, должность, подразделение и дата приёма. Роль, руководитель, почта и остаток отпуска импортом не меняются. Новые записи создают приглашения на 7 дней, без фиктивных Auth-профилей. Коды доступны только в ответе первого успешного применения; HR скачивает CSV и передаёт коды лично. Письма этим действием не отправляются. Новый сотрудник сам задаёт пароль и подтверждает почту. Начальный отпускной остаток — 0; подтверждённый кадровый остаток вносится через существующую сверку.

## Адаптация

HR собирает неизменяемую последовательность опубликованных версий курсов, задаёт каждому шагу срок в днях и назначает сотруднику. Можно назначать автоматически при регистрации для одной роли. Для каждого типа роли возможна одна активная автоматическая траектория; остальные назначаются вручную.

Автоматически назначается первый незавершённый курс. После успешного теста открывается следующий; планировщик и чтение плана восстанавливают шаг при временном сбое. Срок считается от открытия шага, а не регистрации всей траектории. Уже пройденные версии засчитываются, существующие сроки назначений сохраняются; отсутствующий срок устанавливается из плана. Отдельно назначенный курс остаётся доступным независимо от плана.

Архивация запрещает новые назначения, сохраняя начатые планы. Для изменения содержания HR создаёт новую траекторию. Сотрудник видит текущий шаг, сроки и прогресс; руководитель — план выбранного сотрудника своей команды.

## Сводки Jana

Кнопка «Что требует внимания?» возвращает факты из текущей базы, время проверки и прямые ссылки. Сотрудник получает свои ожидающие заявки и просроченные курсы. Руководитель — доступные ему согласования, обучение текущей команды и пересечения доступных отпусков. HR дополнительно видит очередь оформления.

Состав данных ограничивается серверной ролью и существующими правами доступа. Временное замещение не расширяет доступ к кадровым профилям и обучению. Пересечения учитывают пары ожидающих/согласованных отпусков; это информационный сигнал, а не автоматический отказ или оценка достаточности персонала. Сводки вычисляются программно, персональные данные не отправляются в LLM; OpenAI-ключ для этой функции не нужен.

## Напоминания

`workflow-worker` включён в обычный Docker Compose, цикл раз в минуту. По умолчанию: напоминание через 48 календарных часов, эскалация в HR через 96 часов, уведомление о курсе за 3 дня. Отсутствие доступного согласующего/заместителя, в том числе при согласованном отпуске, эскалируется без ожидания 96 часов. HR также получает напоминания об оформлении. Просрочка курса уведомляет сотрудника, текущего руководителя и HR.

Один ключ на сущность, этап, получателя и срок защищает от дублей. Несколько воркеров не проводят один цикл одновременно. Эскалация не принимает решение, не меняет маршрут и не выдаёт права: HR действует в рамках уже существующих полномочий. Уведомления только внутри портала; email/SMS/push в эту функцию не входят.

При запуске без Docker нужен отдельный процесс:

```powershell
.\.venv\Scripts\python.exe -m scripts.workflow_worker
```

Разовая проверка: `python -m scripts.workflow_worker --once` или кнопка HR «Проверить сейчас». В интерфейсе показано время последнего цикла.

## Развёртывание и проверка

Применить `0011_hr_workflows.sql`, затем `0012_employee_import.sql` и `0013_invitation_email.sql` после миграций 0001–0010. Для текущего проекта Supabase все три миграции уже применены. У всех восьми новых таблиц проверены RLS и запрет прямого чтения ролям anon/authenticated. Команды доступны только серверу, пользовательские права дополнительно проверяются API и SQL.

```powershell
docker compose up -d --build api workflow-worker
```

Проверки: 413 тестов Python с настоящей изолированной PostgreSQL, 31 тест фронтенда. [Живой прогон](performance/hr-workflows-live.json) прошёл 52 API-вызова в Docker + Supabase на маркированных вымышленных аккаунтах: согласование → документ, CSV/XLSX → приглашение, последовательное завершение двух курсов, три ролевые сводки, повтор напоминаний без дублей. Тестовое приглашение отозвано, учебные тестовые курсы и траектория архивированы; письма не отправлялись. Проверка UI и размеров сохранена отдельно в `docs/design/hr-workflows-ui-verification.json`.

Скрипт `scripts/verify_hr_workflows_live.py` ограничен текущим тестовым проектом и существующими маркированными jury-аккаунтами; checkpoint в `.local` обеспечивает безопасный повтор.
