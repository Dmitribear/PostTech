# Регистрация и восстановление доступа

Рабочий путь: код приглашения → данные аккаунта → подтверждение почты → приветствие → рабочее пространство. Роль, подразделение, руководитель и кадровые данные назначаются HR. Выбор роли на экране знакомства относится только к демоверсии.

## Настройки Supabase

Включите Email provider и Confirm email. Отключённый Confirm email автоматически подтверждает адрес без проверки владельца; такой режим не соответствует сценарию регистрации. [Описание настройки](https://supabase.com/docs/guides/auth/general-configuration).

В Authentication → Emails → Confirm signup добавьте код `{{ .Token }}`. Стандартное письмо со ссылкой само по себе не даёт пользователю код для экранной формы. Минимальный шаблон:

```html
<h2>Подтвердите почту в PostTech</h2>
<p>Введите этот код на странице регистрации:</p>
<p style="font-size:32px;font-weight:700;letter-spacing:6px">{{ .Token }}</p>
<p>Если вы не создавали аккаунт, проигнорируйте письмо.</p>
```

Для восстановления пароля установите [recovery.html](templates/recovery.html) в Authentication → Emails → Reset password; рекомендуемая тема — «Восстановление пароля PostTech». В обоих шаблонах нужен `{{ .Token }}`. Вход по magic link в приложении не реализован. Не вставляйте в письма пароль или код кадрового приглашения. [Шаблоны Supabase](https://supabase.com/docs/guides/auth/auth-email-templates).

Готовый русский шаблон с оформлением PostTech: [confirm-signup.html](templates/confirm-signup.html). При настройке нового проекта после подключения SMTP скопируйте его в Confirm signup; рекомендуемая тема письма — «Подтвердите почту в PostTech». Шаблон содержит `{{ .Token }}` и не требует внешних изображений. Проверяйте его доставку и отображение на принадлежащем вам тестовом адресе.

Настройте собственный SMTP или Send Email hook для адресов сотрудников. Встроенная почта Supabase предназначена для проверки проекта: отправка разрешена только на адреса участников организации, текущий общий лимит — два письма в час. Наличие настроенных ключей API не подтверждает готовность доставки почты. [Настройка SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

Сверьте длину кода с конфигурацией проекта. Документация размещённого сервиса описывает шесть цифр, а документация локальных шаблонов — восемь; экран и сервер не должны отбрасывать допустимый код из письма. [Локальные шаблоны](https://supabase.com/docs/guides/local-development/customizing-email-templates).

Повторную отправку нужно согласовать с лимитами сервиса. Стандартная задержка для запроса подтверждения — 60 секунд; серверный ответ 429 должен оставлять пользователя на текущем шаге с возможностью повторить позже. [Лимиты Auth](https://supabase.com/docs/guides/auth/rate-limits).

## Проверка личности и прав

- После проверки OTP используйте подтверждённого пользователя из ответа Supabase, а не переданный браузером идентификатор. Проверяйте `email_confirmed_at` и совпадение адреса с приглашением.
- Для проверки почтового кода Python SDK принимает `verify_otp` с `type="email"`. Повтор подтверждения регистрации использует `resend` с `type="signup"`; повтор кода входа — новый вызов `sign_in_with_otp`. [Проверка кода](https://supabase.com/docs/reference/python/auth-verifyotp), [повторная отправка](https://supabase.com/docs/reference/python/auth-resend).
- Не считайте ответ `sign_up` доказательством создания нового аккаунта: для уже существующего адреса сервис может вернуть скрывающий существование аккаунта объект. Профиль можно связывать только после успешного подтверждения или входа владельца. [Создание пользователя](https://supabase.com/docs/reference/python/auth-signup).
- Кадровое приглашение должно быть одноразовым, ограниченным по времени и привязанным к адресу. Храните хеш кода; создание профиля и погашение приглашения должны проходить одной транзакцией.
- Уже существующий профиль нельзя повышать до новой роли через повторное приглашение. Значения `role` и `employee_id` из браузера или изменяемого `user_metadata` не дают прав.
- Каждый пользовательский Auth-запрос получает отдельный экземпляр клиента с отключёнными `auto_refresh_token` и `persist_session`; общий только HTTP-пул. `persist_session=False` всё равно оставляет сессию внутри экземпляра SDK, поэтому совместное использование одного Auth-клиента разными пользователями недопустимо.

## Самостоятельное восстановление пароля

На экране входа ссылка «Забыли пароль?» открывает путь: корпоративная почта → код из письма и новый пароль → возврат ко входу. Автоматический вход после смены пароля не выполняется.

| Запрос | Результат |
| --- | --- |
| `POST /api/v1/auth/password-reset` с `{email}` | Нейтральное сообщение и `retry_after: 60`; не раскрывает наличие аккаунта. |
| `POST /api/v1/auth/password-reset/confirm` с `{email, token, password}` | Проверка OTP, смена пароля, сообщение об успехе без токенов сессии. |

Отправка использует `reset_password_for_email`; повторная отправка — тот же метод. Сервер проверяет код через `verify_otp(type="recovery")`, подтверждённый адрес и совпадение пользователя сессии, затем вызывает `update_user` на том же изолированном клиенте. Административный сброс пароля по email не используется. Пароль должен содержать 8–128 символов, заглавную букву и цифру. [Восстановление Supabase](https://supabase.com/docs/reference/python/auth-resetpasswordforemail), [обновление пароля](https://supabase.com/docs/reference/python/auth-updateuser).

При слабом пароле проверка останавливается до погашения кода. Неверный, истёкший или использованный код требует нового. Если проверка кода уже прошла, а обновление пароля завершилось сетевой ошибкой, код может быть погашен, а пароль — уже изменён: интерфейс предлагает попробовать вход с новым паролем либо запросить новый код. Успех не возвращает пользовательскую сессию. После смены выполняется global sign-out; при временном сбое отзыва успешная смена пароля не превращается в ложную ошибку. Старые access JWT могут оставаться действительны до своего истечения. [Выход из сессий](https://supabase.com/docs/reference/python/auth-signout).

У Supabase recovery и magiclink используют общий тип хранимого recovery-токена; `type="recovery"` нельзя считать криптографическим различением этих двух сценариев. Signup-код хранится отдельно. Приложение не выдаёт magic-link вход и проверяет владение почтой через Supabase. [Реализация проверки](https://github.com/supabase/auth/blob/master/internal/api/verify.go).

Локальные ограничения: одна отправка на адрес за 60 секунд, 10 отправок с IP за 10 минут, 5 подтверждений на адрес и 30 с IP за 5 минут. Повторная отправка в период ожидания имеет тот же нейтральный ответ; IP-ограничения возвращают `429` и `Retry-After`. Хранятся только временные HMAC-ключи счётчиков, без адресов и кодов. Счётчики находятся в памяти процесса и дополняют ограничения Supabase; для нескольких процессов нужен общий лимит на уровне прокси. Нейтральность ответа не является проверкой одинакового времени обработки.

### Статус SMTP / Resend

Выбран ограниченный тест без собственного домена: Resend разрешает отправлять от `onboarding@resend.dev` **только на email владельца аккаунта Resend**. Для отправки другим получателям позже понадобится подтверждённый домен. [Ограничения тестового домена Resend](https://resend.com/docs/knowledge-base/403-error-resend-dev-domain).

17 октября 2026 года SMTP Resend настроен в Supabase для этого ограниченного теста. После перезагрузки страницы подтверждены включённый custom SMTP и сохранённый пароль провайдера. Используется ключ Resend только с правом отправки; прежний ключ неудачной попытки настройки удалён. Отправитель — `onboarding@resend.dev`, имя — PostTech. Email владельца, ключ и другие секреты в документацию не включены.

В Supabase сохранены русские шаблоны Confirm signup и Reset password с `{{ .Token }}`; предпросмотр обоих проверен. Для владельца создано приглашение с ролью `worker`, нулевым остатком отпуска, без руководителя и со сроком 24 часа. Код сохранён только в игнорируемом локальном файле. Создание приглашения не отправляет письмо и не создаёт Auth-аккаунт.

**Регистрация и восстановление через настоящие письма завершены.** Resend показал `Delivered` для обоих писем. Владелец получил восьмизначный код и самостоятельно подтвердил почту; в браузере открылась главная. После запроса восстановления владелец самостоятельно сменил пароль и подтвердил успешный повторный вход. Финальная серверная проверка обнаружила один подтверждённый Auth-аккаунт, один профиль `worker` и одно использованное приглашение. Завершение смены пароля и повторный вход зафиксированы по сообщению владельца; его пароль агент не получал. Нейтральный ответ `/password-reset` сам по себе подтверждает принятие запроса, а не доставку: ошибки провайдера, раскрывающие наличие адреса, намеренно не возвращаются пользователю.

Во время проверки исправлен ввод OTP: реальные формы регистрации и восстановления сразу показывают восемь ячеек. Регистрация отправляет код только по кнопке «Подтвердить» или Enter, без автоматической отправки шестизначного префикса. Сервер принимает строго 6 или 8 цифр; длины 5, 7 и 9 отклоняет. На шаге аккаунта ссылка «Уже есть код из письма» позволяет вернуться к подтверждению после повторной активации того же приглашения, без создания второго аккаунта и повторного ввода пароля. Проверки Auth/recovery: 59 passed; клиентские тесты: 26 passed; production build прошёл.

## Приёмочная проверка

1. Действительный, неверный, просроченный, отозванный и уже использованный код приглашения.
2. Изменение email или роли вручную в запросе; попытка использовать приглашение другого сотрудника.
3. Слабый пароль и повторная регистрация уже существующего адреса.
4. Верный, неверный, истёкший и повторно использованный почтовый код; вставка кода целиком; повтор отправки до и после задержки.
5. Недоступность почтового сервиса и лимит 429: нет ложного сообщения об отправке или успешном создании профиля.
6. Два параллельных подтверждения: один кадровый профиль, одно погашение приглашения; повтор после сетевого сбоя восстанавливает предсказуемое состояние.
7. Успех: профиль имеет назначенную HR роль; главная, заявки и обучение доступны с соответствующими правами. Выход и повторный вход работают.
8. Мобильный экран 390 px: поля, ошибки, код, кнопки и экранная клавиатура не перекрывают действия. Навигация назад не смешивает данные двух приглашений.
9. Демоверсия явно обозначена и не создаёт реальные аккаунты, письма или кадровые записи.
10. Восстановление: неверный код, повторное использование, слабый и прежний пароль, задержка отправки, обновление после сетевого сбоя. После успеха старый пароль не работает, новый открывает тот же аккаунт, прежняя refresh-сессия отозвана.
