# Docker и локальная Jana

Основной запуск использует три контейнера:

| Сервис | Назначение |
| --- | --- |
| frontend | Собранный React, Nginx, проксирование /api/ |
| api | FastAPI, авторизация, бизнес-логика, обращения к Supabase и AI |
| integrations | Два независимых процесса: напоминания/обучение и доставка outbox в 1С/Documentolog |

Supabase остаётся внешним: база и Auth не переносятся и не очищаются. Локальная модель — дополнительный, четвёртый контейнер. Самостоятельный Supabase потребует дополнительных сервисов PostgreSQL, Auth и REST; обычный PostgreSQL не заменяет используемый Supabase API.

```powershell
docker compose up --build -d --remove-orphans --wait
docker compose ps
docker compose logs --tail 100 api integrations
```

Открыть http://localhost:8000. Только frontend публикует порт, по умолчанию на 127.0.0.1. POSTTECH_HTTP_PORT меняет порт. Для публичного сервера нужно отдельно настроить HTTPS и внешний reverse proxy. Команда remove-orphans удаляет устаревшие контейнеры воркеров этого Compose-проекта; данные внешнего Supabase не затрагивает. Docker restart не пересобирает код.

Интеграции отправляют данные только при включённых INTEGRATION_1C_ENABLED / INTEGRATION_DOCUMENTOLOG_ENABLED. При падении дочернего процесса supervisor завершает контейнер и Docker перезапускает оба процесса. Ошибки отдельных циклов обрабатываются существующими воркерами; наличие запущенного контейнера само по себе не подтверждает доступность БД или доставку.

## Локальная модель

1. Скачать совместимую instruct-модель GGUF, например Qwen3-8B Q4_K_M, из доверенного репозитория. Проверить лицензию и контрольную сумму. Автоматического скачивания в старте нет.
2. Указать в .env полный путь, например `JANA_MODEL_PATH=E:/Models/Qwen3-8B-Q4_K_M.gguf`.
3. Запустить:

```powershell
docker compose -f compose.yaml -f compose.ai.yaml up --build -d --remove-orphans --wait --wait-timeout 600
```

Файл compose.ai.yaml переключает API на local и подключает llama.cpp по внутреннему адресу jana-reader:8081. Порт модели наружу не открыт. Модель монтируется read-only, отсутствующий файл вызывает ошибку. Конфигурация CPU: 4 потока, контекст 8192, один параллельный запрос. Для NVIDIA нужен CUDA-образ и доступ GPU через NVIDIA Container Toolkit; текущий файл GPU не включает.

Возврат к основному провайдеру: убрать JANA_PROVIDER=local из .env, если задавали вручную, и выполнить обычную команду с compose.yaml и --remove-orphans. Для OpenAI необходим API-ключ.

Текущая локальная Jana выбирает и проверяет выдержки из актуальных HR-документов, а не свободно сочиняет ответы. Нужны опубликованные материалы с reviewed_at/review_due_at. Если база не помещается в контекст, ответ отклоняется: масштабирование потребует поиска релевантных фрагментов вместо передачи всей базы. Без реальной модели качество и задержки не подтверждены.

## Планирование ресурсов

Ориентиры, не результаты нагрузочного теста PostTech:

- Портал с внешней БД и внешним AI: начать с 2–4 vCPU и 4–8 ГБ RAM, затем измерить нагрузку.
- CPU-модель класса 8B Q4: 4–8 современных ядер, 16 ГБ RAM минимум для небольшого стенда; 24–32 ГБ дают запас ОС, Docker и контексту. Файл весов около 5 ГБ, память выполнения больше.
- Для интерактивной многопользовательской работы рассмотреть GPU 12–16 ГБ VRAM и 32 ГБ системной RAM. Требования растут с контекстом и числом одновременных запросов; скорость необходимо измерить до покупки сервера.

Сложность Docker-запуска небольшая, основная работа — подбор модели, проверка русского/казахского, качество отказов, измерение задержек и мониторинг. Локальный AI не делает весь портал автономным: Supabase и отправка email по-прежнему используют внешние сервисы.

Источники: [официальный Docker llama.cpp](https://github.com/ggml-org/llama.cpp/blob/master/docs/docker.md), [официальные файлы Qwen3-8B GGUF](https://huggingface.co/Qwen/Qwen3-8B-GGUF/tree/main).
