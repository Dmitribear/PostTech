# Проверка сценариев на настоящем Supabase

`scripts/verify_live_workflow.py` проверяет базовый отпуск сотрудника, а `scripts/verify_role_scenarios.py` — расширенные роли, Academy и Jana. Оба работают с локальным API, подключённым к Supabase Auth и PostgreSQL, без подмены ответов и демонстрационного режима фронтенда. Нужен Python 3.11+; дополнительных библиотек для этих проверок нет.

## Подготовка

1. Настройте серверное подключение к тестовому проекту Supabase в `.env`, примените миграции `0001_digital_hr.sql` и `0002_request_workflow.sql`.
2. Создайте отдельную фиктивную пару сотрудник/руководитель командой ниже. Ей нужны серверный ключ в `.env` и установленная схема. `--project-ref` должен совпадать с проектом в `.env`; для текущего проекта используется `zcsoipcwymhowmvnytxf`.

```powershell
.\.venv\Scripts\python.exe scripts/provision_live_accounts.py --project-ref zcsoipcwymhowmvnytxf
```

Подготовка создаёт подтверждённые аккаунты `e2e.employee+<суффикс>@posttech.demo` / `e2e.manager+<суффикс>@posttech.demo`, профили с источником `posttech-live-check`, кодами `LIVE-EMP-<суффикс>` / `LIVE-MGR-<суффикс>` и связь подчинения. Она сохраняет пароли в Git-игнорируемом `.local/live-credentials.json`. Повтор использует те же тестовые аккаунты; существующие чужие аккаунты, пароли и профили не перезаписываются. Проверочный скрипт читает этот файл без дополнительных настроек.

Перед подготовкой проверьте у `service_role` права `SELECT` и `INSERT` на `public.employee_profiles`: миграция `0002` явно выдаёт только `SELECT`, а `INSERT` зависит от исходных прав проекта. Если вставка профиля недоступна, подготовка остановится после создания Auth-аккаунта. После исправления прав повторите команду с тем же файлом `.local/live-credentials.json`.

3. Запустите API на `http://127.0.0.1:8000`. У сотрудника должна быть роль `worker`, у руководителя — `manager`, сотрудник должен находиться в его прямом подчинении.
4. Альтернатива подготовке отдельной пары: используйте уже созданные подтверждённые Auth-аккаунты `employee@posttech.demo`, `manager@posttech.demo`, `hr@posttech.demo` и примените `database/seed.sql` после их создания. Подробности: [сценарий отпуска](leave-workflow.md). Эти профили должны иметь коды `DEMO-EMP-001` / `DEMO-MGR-001` и источник `mock-1c-zup`. В этом варианте убедитесь, что `.local/` исключена из Git, и заполните `.local/live-credentials.json` локально:

```json
{
  "employee": {"email": "employee@posttech.demo", "password": "<локальный пароль сотрудника>"},
  "manager": {"email": "manager@posttech.demo", "password": "<локальный пароль руководителя>"}
}
```

Вместо файла можно передать пароли через переменные окружения `POSTTECH_EMPLOYEE_PASSWORD` и `POSTTECH_MANAGER_PASSWORD`. Email по умолчанию соответствует seed; переменные `POSTTECH_EMPLOYEE_EMAIL` / `POSTTECH_MANAGER_EMAIL` позволяют задать другие фиктивные адреса в домене `posttech.demo`. Значения окружения имеют приоритет над файлом. Не передавайте пароли в аргументах командной строки.

## Запуск

Сначала можно проверить вход, роли, связь сотрудника с руководителем и доступность списков без создания заявки:

```powershell
.\.venv\Scripts\python.exe scripts/verify_live_workflow.py --preflight-only
```

Полный сценарий создаёт **одну** явно помеченную тестовую заявку на отпуск, затем согласует её:

```powershell
.\.venv\Scripts\python.exe scripts/verify_live_workflow.py
```

Оба вызова сначала выполняют настоящий вход через `/api/v1/auth/login`. Проверка без bearer-токена должна вернуть `401`. До первого изменения заявки проверяются оба HR-профиля, ожидаемые demo-поля, разные Auth ID и ID профилей, связь `manager_id`, состав команды и доступность списков.

Полный запуск проверяет:

- Создание отпуска с уникальным `Idempotency-Key`, совпадение полей заявки и её присутствие в списках сотрудника и руководителя.
- Повтор создания с тем же ключом: та же заявка, та же история и одно уведомление руководителю.
- Попытку сотрудника согласовать собственную заявку: `403`, данные не меняются.
- Решение руководителя: `approved`, правильный автор и время, история `created → approved`, одно уведомление сотруднику.
- Повтор решения: неизменные данные заявки, история и уведомления.
- Просмотр сотрудником решения, совпадение истории у обеих ролей, отметку уведомления как прочитанного и повторную отметку с тем же временем первого прочтения.

Успех возвращает код процесса `0` и JSON со статусом `passed`, ID заявки и участников, датами и счётчиками. Ошибка возвращает `1` и краткую диагностику. Пароли, токены, тела HTTP-ответов, ФИО и кадровые данные не выводятся.

## Повтор после прерывания

До отправки заявки скрипт сохраняет уникальный ключ, даты, ID участников и адрес API в `.local/live-workflow.json`. В нём нет паролей или токенов. **Сохраняйте этот файл и повторяйте ту же команду**: даже если ответ создания или согласования потерян, повтор продолжает ту же заявку. Завершённый сценарий также проверяется повторно без создания новой заявки. Профили и адрес API должны совпадать с checkpoint.

По умолчанию даты отпуска — через 30 дней от текущей даты в часовом поясе пользователя UTC+5, длительность — два календарных дня. `--start-date YYYY-MM-DD` задаёт дату первого запуска; существующие даты checkpoint менять нельзя. `--base-url` поддерживает другой локальный порт и необязательный суффикс `/api/v1`; адрес должен быть loopback. HTTP-переадресации отключены, чтобы не пересылать секреты на другой адрес.

`--credentials` и `--checkpoint` позволяют выбрать другие Git-игнорируемые файлы внутри репозитория. Другой или удалённый checkpoint означает новый запуск и новую тестовую заявку. Не удаляйте его для повторной попытки. Файл `.lock` предотвращает одновременный запуск с одним checkpoint. После аварийного завершения удалять можно только зависший `.lock`, предварительно убедившись, что процесс больше не работает.

## Границы проверки

Скрипт проверяет API → Supabase Auth → PostgreSQL, без браузерной автоматизации. Он оставляет согласованную синтетическую заявку и связанные события/уведомления в тестовом проекте как свидетельство проверки; удаления через API нет. Чтение уведомления — единственное изменение кроме создания и согласования этой заявки. Авторизация в Supabase создаёт обычные пользовательские сессии.

Базовый сценарий не проверяет другую команду, HR-самосогласование, параллельную нагрузку, доставку email, внешние интеграции с 1С/ЭЦП или списание остатка отпуска. Роли и границы команд дополнительно проверяет расширенный сценарий ниже. По контракту MVP согласование не создаёт кадровый документ и не списывает отпуск. Успешный `/health/ready` сам по себе не доказывает работоспособность схемы; итоговое подтверждение — только фактический `passed` полного сценария.

## Расширенная проверка ролей, Academy и Jana

`scripts/verify_role_scenarios.py` использует отдельные семь фиктивных аккаунтов: сотрудник, его руководитель, директор, два HR, сотрудник другой команды и сотрудник без руководителя. Предыдущая тестовая пара и её заявки остаются независимыми. Все проверяемые изменения выполняются через публичный API приложения; локальная база или подменённые HTTP-ответы не используются.

Перед запуском нужны миграции `0001`–`0004`, три курса из `database/seed_academy_demo.sql` и опубликованные статьи базы знаний из `database/seed.sql`. Учебный seed не назначает курсы автоматически и не заменяет существующие записи с теми же ID. Для текущего тестового проекта:

```powershell
.\.venv\Scripts\python.exe scripts/provision_scenario_accounts.py --project-ref zcsoipcwymhowmvnytxf
.\.venv\Scripts\python.exe scripts/verify_role_scenarios.py
```

Пароли находятся только в `.local/scenario-credentials.json`; состояние проверки — в `.local/scenario-run.json`. До изменений проверяются реальные Auth ID, коды `SCENARIO-…`, источник `posttech-scenario-check`, роли и вся цепочка подчинения. Удаление checkpoint означает потерю ключей повторной отправки: сохраняйте его и повторяйте ту же команду после сбоя. Для другого локального порта доступен `--base-url`; `--credentials` и `--checkpoint` принимают только Git-игнорируемые файлы внутри проекта.

Сценарий создаёт пять помеченных тестовых заявок: отпуск сотрудника, отпуск руководителя, отпуск HR, аванс сотрудника с отказом и отпуск сотрудника с отменой. Проверяет маршруты сотрудник → руководитель, руководитель → директор, HR → другой HR и отсутствие руководителя → HR. Последний маршрут проверяется без дополнительной заявки. Решения, отказы самосогласования и доступа другой команды, обязательная причина отказа, запрет прошлых дат и пересечения с активным отпуском, события, уведомления и повторы проверяются по реальным ответам API. Фильтр согласования должен исключать собственные заявки, включая HR. Остатки отпусков всех семи профилей сравниваются до и после сценария.

В Academy назначаются три разных учебных курса сотруднику, руководителю и HR. Для каждого проверяются материал и отметка 90%, неуспешная попытка с сохранением состояния «В процессе», успешная вторая попытка, неизменность завершения при поздних обновлениях, командный обзор и отсутствие дополнительных попыток/уведомлений при повторах. Сотрудник не может назначать обучение, а руководитель — назначать его сотруднику другой команды или читать его командный прогресс. API не должен публиковать правильные ответы; решения для автоматической проверки читаются только из локального фиктивного seed, не сохраняются в checkpoint и не выводятся.

Для Jana проверяются четыре подтверждённых вопроса: оформление отпуска, запрос аванса, просмотр статуса заявки и доступ к кадровым сведениям. Каждый возвращённый источник открывается через API, а текст ответа проверяется на наличие фрагмента источника. Неизвестная норма количества отпускных дней и просьба проигнорировать инструкции/принять кадровое решение должны вернуть отказ с предложением обратиться в HR. Эти проверки подтверждают работу установленной базы и выдачи источников; они не подтверждают наличие внешней AI-модели, если используется честно обозначенный поиск по базе.

Успех — код `0` и JSON `passed` с флагами проверок, ID и статусами заявок, ID назначений и счётчиками. Пять заявок, три назначения и шесть попыток остаются в тестовом проекте. Это API-проверка; прохождение всех расширенных действий через интерфейс фиксируется отдельно.
