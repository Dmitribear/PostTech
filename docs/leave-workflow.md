# Отпуск: сквозной сценарий через API

Этот сценарий реализует путь Digital HR из Challenge 02: вход → роль и профиль → создание заявки → решение руководителя или HR → история → уведомление сотруднику. UI для его проверки не нужен: доступны Swagger по `/docs` и [готовые HTTP-запросы](../examples/leave-workflow.http).

Базовый адрес локального API: `http://localhost:8000/api/v1`. Ответы — JSON. Во всех защищённых запросах используйте `Authorization: Bearer <access_token>` соответствующего пользователя.

## Подготовка базы

1. Настройте `.env` по [README](../README.md#supabase-setup-and-demo-data). Для сценария отпуска ключ OpenAI не нужен.
2. В новой Supabase-базе примените [0001_digital_hr.sql](../database/migrations/0001_digital_hr.sql), затем [0002_request_workflow.sql](../database/migrations/0002_request_workflow.sql). Если первая миграция уже применена, нужна только вторая.
3. Создайте три тестовых Auth-аккаунта, указанных ниже, затем выполните [seed.sql](../database/seed.sql). Seed добавляет в том числе историю демонстрационных заявок и допускает повторный запуск.
4. Запустите `docker compose up --build`. Откройте `/docs` или HTTP-файл.

SQL выполняет администратор проекта в Supabase SQL editor. API не применяет миграции при запуске. Проверка `/health/ready` подтверждает только возможность инициализации клиента, а не наличие таблиц и RPC. Перед демонстрацией выполните весь сценарий на тестовой базе.

## Подготовка учётных записей

| Auth email | Роль после seed | Назначение |
| --- | --- | --- |
| `employee@posttech.demo` | `worker` | Создаёт заявку, видит решение и своё уведомление. |
| `manager@posttech.demo` | `manager` | Прямой руководитель тестового сотрудника, рассматривает его заявку. |
| `hr@posttech.demo` | `hr_admin` | Может рассматривать заявки других сотрудников независимо от команды. |

В Supabase Authentication → Users создайте пользователей с этими email, задайте свои тестовые пароли и подтвердите аккаунты, если этого требует настройка Auth. `seed.sql` связывает существующих Auth-пользователей с профилями по этим email и задаёт `manager_id` сотрудника. Если запустить seed до создания пользователей, профиль для отсутствующего аккаунта не появится: создайте аккаунт и повторите seed.

Пароли и токены не включены в репозиторий. В HTTP-примере заменяйте заглушки локально или используйте приватное окружение своего HTTP-клиента; не коммитьте заполненный файл.

Для другого зарегистрированного аккаунта `POST /auth/register` создаёт только Auth-запись. Администратор связывает её UUID с существующим кадровым профилем. Например, после подстановки двух реальных UUID в SQL editor:

```sql
-- Выполняет администратор, предварительно проверив соответствие сотрудника аккаунту.
update public.employee_profiles
set auth_user_id = '<AUTH_USER_UUID>'::uuid
where id = '<EMPLOYEE_PROFILE_UUID>'::uuid;
```

Это перепривязывает существующий профиль и прекращает доступ к нему прежнего Auth-аккаунта. Для нового сотрудника администратор создаёт отдельную запись `employee_profiles` со всеми обязательными полями из первой миграции. Роль не передаётся в login/register: сервер получает её из профиля. При отсутствии профиля HR endpoints возвращают `403`.

## Порядок проверки

| Шаг | Кто и запрос | Ожидаемый результат |
| --- | --- | --- |
| 1 | Сотрудник: `POST /auth/login` с email и password. | `200`, `access_token` и `refresh_token`. |
| 2 | Сотрудник: `GET /profile`. | `200`, `role=worker`, кадровые поля, UUID профиля и `manager_id`. Остаток отпуска доступен только для чтения. |
| 3 | Руководитель: login, `GET /profile`, `GET /team`. | `role=manager`; тестовый сотрудник присутствует в команде. UUID руководителя совпадает с `manager_id` сотрудника. |
| 4 | Сотрудник: `POST /requests` с `request_type=leave`, датами, комментарием и UUID-заголовком `Idempotency-Key`. | `201`, новая заявка со статусом `pending`. Сохраните её `id`. Созданы событие `created` и уведомление руководителю; при отсутствии руководителя уведомляются HR. |
| 5 | Сотрудник: `GET /requests?request_type=leave`, затем `GET /requests/{id}` и `/history`. | Заявка присутствует в списке; карточка показывает её поля; история содержит событие создания. |
| 6 | Руководитель: `GET /notifications?request_id={id}`, `GET /requests?status=pending&request_type=leave`. | Уведомление о новой заявке содержит её `request_id`; список включает заявки разрешённой команды. |
| 7 | Руководитель: `PATCH /requests/{id}/review` с `status=approved` и `reviewer_comment`. | `200`, сохранены решение, автор и время; появилось событие `approved` и уведомление сотруднику. |
| 8 | Сотрудник: `GET /requests/{id}`, затем `/history`. | Статус `approved`; в истории события `created` и `approved` с авторами и временем. |
| 9 | Сотрудник: `GET /notifications?request_id={id}`, затем `POST /notifications/{notification_id}/read`. | Видно своё уведомление с нужным `request_id`; отметка прочтения возвращает `read_at`. Повтор возвращает то же время первого прочтения. Используйте ID уведомления, не заявки. |

Вместо шага 7 HR может принять решение по чужой заявке. Для демонстрации отклонения создайте **новую** заявку с **новым** `Idempotency-Key` и отправьте `status=rejected`: возникнут событие `rejected` и уведомление сотруднику. Один запрос на review принимает одно окончательное решение, поэтому уже одобренную заявку нельзя превратить в отклонённую.

Заявка, её событие истории и уведомления сохраняются атомарно. Ошибка одной из этих операций откатывает весь соответствующий create/review, а не оставляет пользователю частично выполненное действие.

## Контракт заявок

### Создание и повторная отправка

```http
POST /api/v1/requests
Authorization: Bearer <EMPLOYEE_ACCESS_TOKEN>
Idempotency-Key: 6e3d6480-f4ce-4791-b63e-138409431901
Content-Type: application/json

{
  "request_type": "leave",
  "start_date": "2026-11-09",
  "end_date": "2026-11-13",
  "comment": "Демо-заявка на отпуск"
}
```

Обе даты обязательны; дата окончания не может быть раньше начала. Для отпуска нельзя передавать сумму `amount`. Комментарий — до 2000 символов. Сотрудник определяется по bearer token: дополнительные поля `employee_id`, роль и другие неизвестные поля в теле создания или review отклоняются с `422`.

Заголовок `Idempotency-Key` необязателен, но полезен при повторном нажатии или потере HTTP-ответа. Его значение — UUID, новый для каждой новой заявки данного сотрудника. Повтор с тем же ключом и теми же полями возвращает `201` и ту же заявку без дополнительных событий и уведомлений. Тот же ключ с другими полями возвращает `409`. Без ключа повторный POST создаёт отдельную заявку. В ответах внутренний ключ не публикуется.

### Список и карточка

`GET /requests` возвращает массив заявок с учётом роли. Допустимы параметры:

| Параметр | Значения |
| --- | --- |
| `employee_id` | UUID профиля сотрудника, доступного текущей роли. |
| `status` | `pending`, `approved`, `rejected`, `cancelled`. |
| `request_type` | `leave`, `advance`. |
| `limit` | От 1 до 100, по умолчанию 50. |
| `offset` | Целое число от 0, по умолчанию 0. |

Пример: `GET /requests?request_type=leave&status=pending&limit=20&offset=0`.

Без `employee_id` сотрудник получает свои заявки, руководитель — свои и прямых подчинённых, HR — все. Фильтр не расширяет права. `GET /requests/{id}` возвращает одну доступную заявку. Поля ответа: `id`, `employee_id`, `request_type`, `status`, `start_date`, `end_date`, `amount`, `comment`, `reviewer_comment`, `reviewed_by`, `reviewed_at`, `created_at`, `updated_at`.

### Решение и история

```json
{
  "status": "approved",
  "reviewer_comment": "Отпуск согласован"
}
```

Такое тело передаётся в `PATCH /requests/{id}/review`. Статус решения — `approved` или `rejected`; комментарий необязателен, до 2000 символов. Рассматривать чужую заявку может её прямой руководитель или HR. **Согласовать собственную заявку не может никто, включая HR.**

Точный повтор решения тем же автором, с тем же статусом и комментарием возвращает `200` без нового события и уведомления. Другая попытка изменить уже принятое решение возвращает `409`. Чтобы повтор был идентичным, отправляйте исходное тело, включая значение комментария.

`GET /requests/{id}/history` возвращает массив событий по времени от создания к решению. У каждого события есть `id`, `request_id`, `actor_id` (может быть `null`, если профиль автора удалён), `event_type` (`created`, `approved`, `rejected`), `from_status` (для создания — `null`), `to_status`, `comment`, `created_at`. Доступ совпадает с доступом к карточке заявки. Для записей, существовавших до второй миграции, миграция восстанавливает создание и сохранённое решение из полей заявки, без отправки исторических уведомлений. Seed также заполняет историю своих demo-заявок. Основной demo-сценарий проверяйте на новой заявке, созданной через API.

## Уведомления

`GET /notifications` возвращает только собственные уведомления, от новых к старым. Фильтры не расширяют доступ, в том числе для HR:

| Параметр | Значения |
| --- | --- |
| `request_id` | Необязательный UUID заявки; выбрать свои уведомления по этой заявке. |
| `unread_only` | `true` — только непрочитанные; по умолчанию `false`. |
| `limit` | От 1 до 100, по умолчанию 100. |
| `offset` | Целое число от 0, по умолчанию 0. |

Пример: `GET /notifications?request_id={request_uuid}&unread_only=true&limit=20&offset=0`.

`POST /notifications/{notification_id}/read` принимает UUID уведомления и возвращает его с `read_at`. Повторный запрос сохраняет время первого прочтения и возвращает `200`. Невалидный UUID даёт `422`; чужое или отсутствующее уведомление — `404`. После прочтения оно исчезнет из списка с `unread_only=true`, но останется в обычном списке. Ответ содержит `id`, `employee_id`, `request_id`, `notification_type`, `title`, `body`, `read_at`, `created_at`.

## Обязательные проверки отказов

| Проверка | Ожидаемый результат |
| --- | --- |
| Защищённый запрос без bearer token. | `401`. |
| Вход есть, но нет связанного HR-профиля. | `403` на HR endpoint. |
| Сотрудник пытается принять решение. | `403`. |
| Руководитель запрашивает карточку/историю или review существующей заявки сотрудника чужой команды. | `403`. |
| Руководитель использует `employee_id` существующего сотрудника чужой команды в фильтре списка. | `403`. |
| HR пытается согласовать собственную заявку. | `403`. |
| Повторный ключ создания используется с другим телом. | `409`. |
| После решения отправляется другое решение или комментарий. | `409`. |
| Некорректный UUID, неизвестный статус, `limit=101`, отрицательный `offset`, неверный диапазон дат. | `422`. |
| Чтение уведомления, принадлежащего другому пользователю. | `404`; чужое уведомление не меняется. |

Для проверки чужой команды используйте существующий профиль с `manager_id`, отличным от UUID проверяемого руководителя, и его существующую заявку. Стандартный seed содержит одну команду. Вторая фиктивная команда для этого негативного сценария создаётся администратором; случайный несуществующий UUID проверяет `404`, а не права доступа. HTTP-файл содержит отдельные переменные для этих ID.

## Автоматические проверки

Обычные API-тесты запускаются через `python -m pytest` после установки `requirements-dev.txt`, без реального Supabase. Для проверки SQL-транзакций, миграций и блокировок установите `python -m pip install -r tests/requirements-db.txt` и задайте `POSTTECH_TEST_DATABASE_URL` на выделенную пустую локальную базу `posttech_test_*`. Нужна административная тестовая учётка с `CREATEDB`/`CREATEROLE` и возможностью создать роль с `BYPASSRLS` и выполнить `SET ROLE`. Команда: `python -m pytest tests/test_request_workflow_db.py -q`.

DB-тесты сами создают и удаляют только свою отдельную базу `posttech_test_<UUID>`. Подключение к Supabase и Docker для них не требуются. Без переменной окружения эти тесты пропускаются. Подготовка подключения и особенности тестовых ролей описаны в [README](../README.md#tests).

## Границы MVP

- Остаток отпуска берётся из профиля и остаётся read-only; после одобрения он не списывается.
- Нет запрета прошлых дат, проверки календаря праздников, пересечений отпусков или придуманного срока предварительной подачи. Подключение таких правил требует утверждённой кадровой политики.
- `cancelled` существует в схеме и фильтре, но отмена заявки в этом сценарии не реализована.
- 1С:ЗУП пока представлена demo-профилями `mock-1c-zup`. Решение по заявке не создаёт реальный кадровый документ и не отправляется в Documentolog.
- Для будущей интеграции нужны адаптер чтения профиля/остатка из 1С и отправка согласованной заявки в Documentolog с внешним ID и синхронизацией статуса. Реальные подключения не нужны для этой API-демонстрации.
