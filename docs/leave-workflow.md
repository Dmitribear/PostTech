# Отпуск: сквозная проверка объединённой ветки

Сценарий: сотрудник создаёт заявку → руководитель или директор согласует первый этап → HR принимает окончательное решение → сотрудник видит историю, уведомление и скачивает календарь. Готовые запросы: [leave-workflow.http](../examples/leave-workflow.http). Полный контракт: [team-backend-contract.md](team-backend-contract.md).

Базовый адрес API: `http://localhost:8000/api/v1`. Для защищённых запросов нужен `Authorization: Bearer <access_token>` соответствующего пользователя.

## Подготовка

Полный порядок SQL для новой локальной тестовой базы задан в [migration-plan.json](../database/migration-plan.json). В нём сохранены обе истории миграций и завершающее согласование `0011_team_workflow.sql`. Не применяйте этот план автоматически к общей Supabase: её история, данные и остатки требуют отдельной проверки. При объединении веток общая база не изменялась.

Проверить весь план без Supabase можно через [check_team_database.py](../scripts/check_team_database.py): runner принимает только явный локальный DSN `posttech_test_*`, создаёт свою временную базу и удаляет её после проверки. `.env` не читается.

Для ручного полного сценария нужна отдельная подготовленная среда с Auth и API. [seed.sql](../database/seed.sql) привязывает уже существующие тестовые Auth-аккаунты по email:

| Email | Роль | Назначение |
| --- | --- | --- |
| `employee@posttech.demo` | `worker` | Создаёт отпуск. |
| `manager@posttech.demo` | `manager` | Руководитель сотрудника, первый этап. |
| `director@posttech.demo` | `director` | Руководитель менеджера; первый этап для его заявок. |
| `hr@posttech.demo` | `hr_admin` | Окончательное решение. |

Если аккаунта нет, seed пропускает его профиль. Создайте и подтвердите тестовый аккаунт в отдельной среде, затем повторите seed. Пароли и токены храните только локально. В HTTP-примере замените заглушки и выберите будущие даты без пересечения с существующими отпусками.

Обычная регистрация требует приглашения HR и подтверждения email. Роль и кадровые данные берутся из приглашения; клиент не может назначить себе роль. Отсутствие HR-профиля даёт `403` на защищённых HR endpoints.

## Последовательность

| Шаг | Запрос и пользователь | Ожидаемый результат |
| --- | --- | --- |
| 1 | Каждый участник: `POST /auth/login`, затем `GET /profile`. | `200`; правильная роль. У сотрудника `manager_id` указывает на руководителя. |
| 2 | Сотрудник: `GET /requests/routing`, `GET /workspace/leave-balance`. | Отправка разрешена, маршрут и согласующие известны, доступных дней достаточно. |
| 3 | Сотрудник: `POST /requests` с отпуском и новым UUID в `Idempotency-Key`. | `201`, `pending`; событие создания, резерв дней, уведомление согласующему. |
| 4 | Руководитель: `GET /requests?scope=review&status=pending`. | Заявка видна; `can_review=true`. |
| 5 | Руководитель: `PATCH /requests/{id}/review`, `status=approved`. | `200`, `pending_hr`. Официальный остаток пока не списан; резерв сохранён. |
| 6 | HR: `GET /requests?scope=review&status=pending_hr`, затем такой же review с `status=approved`. | `200`, окончательное `approved`. Дни списаны один раз, резерв сверён. |
| 7 | Сотрудник: `GET /requests/{id}/history`. | Переходы `pending`, `pending_hr`, `approved` с авторами и временем. |
| 8 | Сотрудник: `GET /workspace/leave-balance`. | `official_days` уменьшился на календарную длительность, действующего резерва этой заявки больше нет. Двойного вычета из `available_days` нет. |
| 9 | Сотрудник: `GET /notifications?request_id={id}`, затем `POST /notifications/{notification_id}/read`. | Только свои уведомления; повторное чтение сохраняет первое `read_at`. |
| 10 | Сотрудник: `GET /requests/{id}/calendar.ics`. | Файл окончательно одобренного отпуска. Импорт в Google Calendar выполняется вручную. |

На каждом этапе повторите идентичный запрос: не должно появляться вторых событий, уведомлений или списания. Если подходящего руководителя нет, маршрут сразу ведёт в HR и первый этап отсутствует. Самосогласование запрещено для всех ролей.

## Создание и проверка дат

```json
{
  "request_type": "leave",
  "start_date": "2026-11-09",
  "end_date": "2026-11-13",
  "comment": "Демо-заявка на отпуск"
}
```

Даты в примере заменяйте по дню проверки. Дни календарные, обе границы включены. Начало не может быть в прошлом по Asia/Qyzylorda; допустимый горизонт — два года. Отпуск не пересекается с собственными `pending`, `pending_hr` и `approved`. Для него запрещено поле `amount`; недостаточный доступный остаток блокирует создание.

`Idempotency-Key` — UUID, отдельный для каждой новой заявки. Повтор с тем же ключом и телом возвращает ту же заявку; изменение тела с тем же ключом даёт `409`. Неизвестные поля, включая подставленный `employee_id` или роль, отклоняются с `422`.

## Согласование и отмена

```json
{
  "status": "approved",
  "reviewer_comment": "Отпуск согласован"
}
```

Тело передаётся в `PATCH /requests/{id}/review`. Допустимы `approved` и `rejected`; при отказе нужна причина. Назначенные руководитель или директор рассматривают первый этап, HR — окончательный. Согласующие фиксируются при создании; смена руководителя не даёт доступ к чужим старым заявкам. Замещение первого этапа допускается только между руководителями и директорами; HR управляет назначением замещения.

Точный повтор того же решения с тем же комментарием безопасен. Другая попытка изменить окончательное решение даёт `409`. Владелец может отменить `pending` и `pending_hr` через `POST /requests/{id}/cancel`; резерв освобождается. Отмена окончательно одобренной заявки и возврат дней этим API не выполняются.

Историю интерпретируйте по `from_status` и `to_status`, не только по `event_type`: первое согласование переводит в `pending_hr`. Статус, история, уведомления, резервы, окончательное списание и outbox сохраняются в одной транзакции.

## Отрицательные сценарии

| Проверка | Результат |
| --- | --- |
| Нет токена или токен недействителен. | `401`. |
| Auth или база временно недоступны. | `503`, без раскрытия внутренних ошибок. |
| Сотрудник пытается согласовать заявку или любой участник согласует свою. | `403`. |
| Руководитель открывает существующую чужую заявку вне своего маршрута и замещения. | `403`. |
| HR пытается пропустить согласование руководителя. | `409`. |
| Календарь скачивается до окончательного одобрения. | `409`. |
| Уже принятое решение изменяется или ключ создания повторяется с другим телом. | `409`. |
| Некорректные UUID, поля, диапазон дат или параметры пагинации. | `422`. |
| Отмечается прочитанным чужое или отсутствующее уведомление. | `404`. |

Для проверки прав используйте существующую заявку другой тестовой команды: случайный UUID проверяет отсутствие записи, а не разграничение доступа.

## Автоматические проверки и границы

API-тесты запускаются через `python -m pytest`. SQL-тестам нужны зависимости из `tests/requirements-db.txt` и явный `POSTTECH_TEST_DATABASE_URL` к отдельной локальной базе. Они создают и удаляют собственные базы `posttech_test_<UUID>`; без DSN пропускаются.

`test_team_workflow_db.py` и `test_team_http_db.py` проверяют полный объединённый план, два этапа, права, повторное и одновременное согласование, резерв, списание, откат и отмену. Старые DB-тесты проверяют отдельные исторические стадии, а не итоговый контракт.

Календарь поддерживает файл `.ics`; автоматической синхронизации с Google нет. Данные 1С — демонстрационные, а outbox для 1С/Documentolog пока только очередь будущей доставки. Расчёт праздников и производственные кадровые правила должны быть подтверждены отдельно.
