# Отпуск, уроки, знания Jana и будущие интеграции

Реализованы шесть улучшений после сравнения конкурента. Код написан под существующие FastAPI, Supabase и React PostTech. Исходники конкурента в приложение не включались.

## 1–2. Баланс и решение по отпуску

В выборе дат и форме видны кадровый остаток, дни на согласовании, одобренные дни до сверки и доступные дни. Отправка сверх доступного остатка блокируется в интерфейсе и в SQL. Блокировка сотрудника защищает от двух одновременных заявок на разные даты, которые вместе превышают остаток. Повтор запроса с прежним ключом сохраняет существующее поведение идемпотентности.

Дни календарные, включая выходные; производственный календарь и правовые исключения не подключены. У решения руководитель видит, что согласование оставляет резерв, а отказ освобождает его. Кадровый остаток автоматически не уменьшается: одобренные резервы остаются до сверки. Это предотвращает двойное списание при последующей загрузке из 1С.

HR: **Управление HR → Остатки отпусков**. Указать новый официальный остаток, выбрать уже учтённые одобренные заявки и основание. Перед подтверждением показан итоговый доступный остаток. Сверка, освобождение выбранных резервов и аудит атомарны; ключ защищает повтор сохранения. Получение расчёта использует один SQL-снимок.

Миграция резервирует существующие ожидающие заявки. Исторические согласованные заявки не резервируются задним числом: невозможно определить, уже учтены ли они в импортированном остатке. При старых избыточных заявках доступный остаток может быть отрицательным; HR должен проверить данные, а не автоматически увеличить баланс.

## 3. Источники Jana

HR: **Управление HR → Знания Jana**. Создание/редактирование черновика, просмотр текста перед публикацией, дата следующей проверки, архив и история действий. Черновик действующего источника сохраняется отдельно и не изменяет текущие ответы. Публикация меняет версию и подтверждает дату проверки. Конкурентные правки защищены номером редакции. Старая цитата не открывает новый текст незаметно: API вернёт 409 и предложит задать вопрос заново. Архив недоступен в новых ответах и по API источника.

Старые источники не объявляются проверенными автоматически. Их существующий режим freshness сохранён; интерфейс явно требует проверки HR. Это управление содержимым, а не новая проверка качества внешней AI-модели.

## 4. Очередь интеграций

HR: **Управление HR → Интеграции**. После нового согласования создаются два события `request.approved`, для `1c` и `documentolog`, в той же транзакции, что и решение. Старые решения не рассылаются задним числом. В payload нет комментариев сотрудника, email и секретов; есть идентификаторы, тип, даты/сумма и данные решения.

Статусы: queued → sending → delivered либо retry → dead. До 8 попыток в одном цикле, экспоненциальная задержка до часа, lease и `FOR UPDATE SKIP LOCKED` для нескольких workers. После истечения lease повтор использует тот же ID события. Устаревший worker не может завершить чужую попытку. История попыток сохранена. HR может вернуть ошибочное событие в очередь; доставленное повторно не запускается.

**Внешняя отправка выключена. Реальные 1С и Documentolog не подключены.** Для каждого направления нужны утверждённый шлюз, HTTPS URL и отдельный случайный HMAC-секрет не короче 32 символов, хранимый только в серверном окружении. Шаблоны переменных — в `.env.example`. Для локального запуска API вне Docker экспортировать эти переменные в окружение процесса. Worker дополнительно читает локальный `.env`.

```powershell
docker compose --profile integrations up -d --build api integration-worker
# Одна итерация без постоянного процесса:
python -m scripts.integration_worker --once
```

Без `INTEGRATION_1C_ENABLED=true` / `INTEGRATION_DOCUMENTOLOG_ENABLED=true` и валидной конфигурации worker даже не забирает события. URL/секреты не доступны через HR API. HTTP timeout 15 секунд, переходы по redirect запрещены. Ответы внешнего сервиса не записываются в ошибки, чтобы не сохранять чужие секреты.

Контракт приёмника:

```json
{"event_id":"UUID", "event_type":"request.approved", "payload":{"schema_version":1,"request_id":"UUID"}}
```

Заголовки `Idempotency-Key: <event_id>`, `X-PostTech-Timestamp: <Unix seconds>`, `X-PostTech-Signature: sha256=<hex>`. Подпись: HMAC-SHA256 от `timestamp + "." + exact_body_bytes`. Приёмник проверяет подпись constant-time сравнением и свежесть timestamp (например, ±5 минут), атомарно сохраняет уникальный event_id до выполнения побочных эффектов, возвращает тот же результат при повторе.

Ожидается HTTP 2xx с `{"event_id":"тот же UUID","accepted":true}`. Просто HTTP 200, иной ID или redirect не считаются доставкой. Семантика **at least once**, не exactly once: при потере ответа внешняя сторона обязана распознать повтор. `delivered` означает подтверждённый приём, а не проведённый кадровый документ. Преобразование в форматы 1С/Documentolog, сопоставление внешних employee IDs, бизнес-callback с номером документа и автоматическая сверка кадрового остатка — задачи следующего подключения.

## 5. Уроки

HR: **Редактор курсов → Уроки**. Добавление, удаление, порядок и тексты уроков. Перевод сохраняет ID и порядок. Опубликованное содержание неизменно; изменения делаются новой версией. Назначенные сотрудники продолжают прежнюю версию.

Сотрудник открывает первый незавершённый урок. Завершение сохраняется отдельно на сервере и переживает перезагрузку. Финальный тест доступен после всех уроков; старый API ручного прогресса не позволяет обойти проверку. Оценка и история попыток остались прежними. Курсы без списка уроков работают по прежнему сценарию одного материала.

## 6. Масштаб и проверка

`scripts/benchmark_extensions.py` создаёт только собственную временную базу на локальном PostgreSQL и удаляет её после прогона. Контрольная база должна быть пустой и называться `posttech_test_*`; Supabase и рабочие сотрудники не используются. Набор по умолчанию: 150 добавленных синтетических сотрудников, по три заявки, по два события на согласование. Параллельная смесь чтений расчёта отпуска, заявок и очереди.

```powershell
$env:POSTTECH_TEST_DATABASE_URL='postgresql://<test-admin>@127.0.0.1:55432/posttech_test_control'
python -m scripts.benchmark_extensions --employees 150 --calls 400 --workers 16
python -m pytest tests/test_extensions_db.py tests/test_integrations.py tests/test_extensions_api.py
```

Результат 17.10.2026: 156 профилей с базовыми фикстурами, 453 заявки, 300 событий; 400 SQL-операций, 16 потоков, 0 ошибок, p95 7,8 мс. Это локальный SQL-бенчмарк, не HTTP, Supabase latency, Auth, AI или внешние системы. Сравнивать его rps напрямую с чужим HTTP-тестом нельзя. Полный отчёт: `performance/extensions.json`.

Проверка рабочего Docker + Supabase: `scripts/verify_extensions_live.py`, только существующие аккаунты с маркером `posttech-jury-fixture`, checkpoint в `.local`. 27 HTTP-вызовов: вход трёх ролей, отпуск и повторное согласование без дублей, два события без внешней доставки, два урока и финальный тест, создание/публикация/архив тестового источника. Публичный отчёт без токенов: `performance/extensions-live.json`.

Миграции 0009 и 0010 установлены в рабочем проекте `zcsoipcwymhowmvnytxf`. Все пять новых таблиц имеют RLS; anon/authenticated не имеют RPC-доступа. Серверный набор: 366 пройденных проверок, затем 8 новых проверок API и дополнительная проверка readiness на старой схеме. Клиент: 31 unit-test; 42 браузерные проверки desktop/mobile, ещё 2 служебных сценария снимков отключены по умолчанию. Браузерные тесты используют демо/подменённый HTTP; отдельный live-отчёт проверяет настоящий Supabase. После обновления выполнен дополнительный просмотр реальных экранов HR и сотрудника при 1440 и 390 px: без ошибок JavaScript и горизонтального переполнения.
