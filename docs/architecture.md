# Архитектура PostTech

React-портал использует `/api/v1`. FastAPI проверяет Supabase Auth и передаёт операции прикладным сценариям. PostgreSQL выполняет транзакционные команды: заявка, событие, уведомление и резерв дней сохраняются согласованно.

## Фронтенд: FSD и Atomic Design

Зависимости направлены вниз: `app → pages → widgets → features → entities → shared`. Прямые импорты между слайсами одного слоя запрещены. Снаружи слайса используется его `index.ts`; алиас `@/` указывает на `src/`.

| Слой | Ответственность | Примеры |
| --- | --- | --- |
| app | Сборка приложения, маршруты, оболочка и провайдеры | App |
| pages | Композиция экрана | requests, team, academy, auth |
| widgets | Самостоятельные крупные блоки | team-learning, hr-workflow |
| features | Действие пользователя | assign-role, invite-employee, leave-calendar-download |
| entities | Представление и правила сущностей | session, employee, hr-request |
| shared | Транспорт, DTO API, локализация, стили и UI-примитивы | api, lib, styles, ui |

В `shared/ui` применён Atomic Design: `atoms` (иконка, аватар, статус, бренд), `molecules` (заголовок, состояния загрузки/ошибки, пагинация), `organisms` (диалог). Бизнес-компоненты живут в FSD-слайсах. Транспортные типы в `shared/api/contracts.ts` описывают серверный контракт. `npm run check:architecture` проверяет направление импортов и публичные API.

## Бэкенд: границы Clean Architecture

| Пакет | Ответственность |
| --- | --- |
| domain | Роли, контекст пользователя, ошибки, чистые правила обработки знаний |
| application/dto | Входные и выходные модели сценариев |
| application/use_cases | Заявки, обучение, приглашения, HR-процессы, доступ и роли |
| application/ports.py | Контракты хранилища, отправки приглашений, интеграций |
| infrastructure | Supabase, HTTP-почта, очередь интеграций, AI-провайдеры, ICS |
| presentation/http | FastAPI-маршруты, проверка токенов, HTTP-ответы |
| bootstrap.py | Подключение конкретных адаптеров к прикладным портам |
| main.py | HTTP-приложение, обработчики ошибок, локализация и SPA |

Domain и application не импортируют FastAPI, Supabase SDK, HTTP-клиенты или внешние адаптеры. Это проверяет `tests/test_architecture.py`. Ошибки хранилища переводятся в `StorageError` / `StorageUnavailable`, затем в безопасный HTTP-ответ. Воркеры вызывают тот же bootstrap, что и HTTP-приложение.

Порт запросов пока отражает операции таблиц/RPC; транзакционные правила остаются в PostgreSQL. Переход на другую СУБД потребует реализации этих команд, а не только замены SDK. При росте новых модулей вводятся предметные репозитории за теми же портами.

## Доступ и согласование

Роль берётся из БД после проверки токена. Регистрация использует роль, назначенную HR в приглашении. Сотрудник видит себя; руководитель и директор — своих прямых подчинённых; HR — кадровые разделы. Директор не получает автоматический доступ ко всем кадровым записям компании.

Маршрут фиксируется при создании заявки. Свой отпуск руководитель или директор отправляет вышестоящему руководителю либо HR; согласовать себя нельзя. Нет согласующего — создание блокируется. Решение и оформление документа HR — разные этапы. При смене роли проверяются актуальные права и наличие подчинённых, записывается аудит; HR не может снять собственную административную роль.

`service_role` остаётся только на сервере. RLS и запрет прямых RPC для `anon` и `authenticated` дополняют проверки приложения. Auth ID не возвращается в карточках сотрудников. Права повторно проверяются внутри SQL-команд.

## Баланс и интеграции

Отпуск резервирует календарные дни в `leave_holds`. Согласование переводит резерв в approved, отказ/отзыв освобождает его. Официальный остаток меняется при сверке кадрового снимка; доступный остаток учитывает ещё не сверенные резервы. Старый триггер списания из main не устанавливается: он списывал бы дни повторно.

Outbox хранит стабильный ID события, попытки, аренду обработчика и повторную доставку. Получатель 1С/Documentolog обязан дедуплицировать ID. HTTP-подтверждение приёма не означает, что документ оформлен. Реальные внешние системы в этой работе не подключались; без получателей HR использует ручное оформление.

## AI Jana

`/ai/ask` сохраняет текущие ответы с источниками, необязательную генерацию OpenAI и оперативные отчёты по правам пользователя. `/ai/local/ask` — отдельный локальный провайдер из Integration с проверкой доказательств и отказом при отсутствии данных. Для него отдельно устанавливаются `requirements-local-ai.txt`, модели и reader. Демо-серверы в `examples/` изолированы от реальных сессий. Проверки контракта не заменяют проверку качества установленной модели.

## Миграции и рост БД

Поддерживаемая последовательность — `database/migrations/0001…0016`. Каждый файл выполняется отдельно, по порядку. `0014` добавляет enum-роли, `0015` использует её после commit; объединять их в одну транзакцию нельзя. Несовместимые старые миграции сохранены в `database/legacy` только для истории.

`0016` добавляет индексы по владельцу/дате, руководителю/ID, непрочитанным уведомлениям, срокам курсов и очереди HR. `/team/page?limit=50&after=<uuid>` отдаёт до 100 сотрудников с курсором и серверной проверкой области доступа. Заявки и уведомления уже имеют ограничение размера страницы. Старый `/team` оставлен для совместимости; перевод оставшихся клиентов и отчётов на порционное чтение — следующий шаг при больших объёмах.

Перед ростом нагрузки нужны измерения EXPLAIN ANALYZE, размера очереди, времени API и числа соединений. Большие индексы в рабочей БД создаются отдельными операционными миграциями CONCURRENTLY, вне транзакции. Чистка аудита и партиционирование вводятся после определения сроков хранения и профиля нагрузки.

Модель рассчитана на одну организацию. Для SaaS нужны tenant_id во всех связанных таблицах, составные ограничения/индексы, tenant-scoped RPC/RLS и миграция данных. Простое добавление nullable tenant_id не создаёт изоляцию. Rate limit восстановления пароля нужно вынести в общее хранилище перед несколькими API-репликами. Горизонтальная масштабируемость нагрузочным тестом пока не подтверждена.

## Проверки

Pytest проверяет сценарии и архитектуру; с POSTTECH_TEST_DATABASE_URL применяет настоящие миграции к временным UUID-базам. Vitest проверяет транспорт и правила UI, Playwright — desktop/mobile. GitHub Actions выполняет эти проверки с PostgreSQL 17. Изменение live Supabase и отправка настоящих писем в эти тесты не входят.
