# PostTech — общий портал с локальной Jana

Ветка `test` объединяет frontend и процессы HR из `test`, роли директора и двухэтапное согласование из `main`, локальную Jana и календарь из `Integration`, проверенные исправления авторизации из `ver2`.

Jana открывается кнопкой **справа вверху** как модальный чат. Модель выбирает точные цитаты из актуальной базы знаний; ссылки открывают исходный материал с проверкой версии. Оперативная сводка портала вычисляется отдельно в рамках прав пользователя и не передаёт персональные записи модели.

## Запуск всего проекта в Docker

Нужен работающий Docker Desktop с Linux containers. Из этой ветки:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/start_docker.ps1
```

Если доступна NVIDIA GPU, добавьте `-Gpu`. Уже скачанную модель можно импортировать:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/start_docker.ps1 -Gpu -ModelDirectory C:\Posttech\.models\reader
```

Сайт: [http://127.0.0.1:8000](http://127.0.0.1:8000). Модель Qwen3.5-9B Q4_K_M около 6,2 ГБ загружается один раз и сохраняется в Docker volume. Python и Node на компьютере для запуска не нужны.

| Локальный аккаунт | Роль |
| --- | --- |
| `employee@posttech.demo` | Сотрудник |
| `manager@posttech.demo` | Руководитель |
| `director@posttech.demo` | Директор |
| `hr@posttech.demo` | HR |

Общий пароль этих четырёх демонстрационных аккаунтов создаётся индивидуально на каждом компьютере и хранится в `POSTTECH_DEMO_PASSWORD` файла `.local/docker.env`. Не публикуйте этот файл. В локальном стенде email подтверждается автоматически; внешняя почта не подключена.

Контейнеры запускают сайт, backend, Jana, PostgreSQL, Auth, PostgREST, внутренний gateway и планировщик. Общая Supabase команды не используется. База и модель сохраняются между перезапусками. Подробности и команды остановки: [Docker](docs/docker-local.md).

## Общие функции

- Четыре роли и серверная проверка доступа. Руководитель/директор рассматривает заявку первым, HR принимает окончательное решение: `pending → pending_hr → approved/rejected`.
- Отпуск резервирует календарные дни включительно. Окончательное одобрение списывает остаток один раз; оформление документа повторно дни не списывает.
- Academy, планы адаптации, приглашения, импорт CSV/XLSX, обращения в HR, уведомления и планировщик напоминаний.
- Отдельное оформление одобренных заявок. Очередь для 1С/Documentolog требует явно настроенных приёмников; текущий локальный стенд их не подключает.
- Индивидуальный `.ics` доступен после окончательного одобрения отпуска. В календаре кнопка «Экспорт в Google Calendar» скачивает общий файл для выбранного месяца и области «Мой календарь»/«Команда». Он создаётся backend-контейнером и импортируется в Google Calendar вручную; автоматической синхронизации нет.
- Jana работает бесплатно без облачного API. В базе 17 вымышленных демонстрационных статей; это описание прототипа, а не утверждённые кадровые правила компании. Проверка цитаты не гарантирует безошибочное понимание любого вопроса.

## Проверки и разработка

[Отчёт объединения](docs/team-integration-report.md), [инструкция команде](docs/team-integration-quickstart.md), [архитектура](docs/architecture.md), [API Jana](docs/ai-jana-api.md).

Для Python-тестов установить `requirements.txt`, `tests/requirements-db.txt` и pytest. DB-тестам нужна отдельная пустая loopback-база `posttech_test_*`; они создают свои одноразовые базы. Все миграции новой базы идут строго по `database/migration-plan.json`. Это не план обновления существующей общей Supabase.

```powershell
python -m pytest -q
npm test --prefix frontend
npm run build --prefix frontend
npm run test:e2e --prefix frontend
```

Без `POSTTECH_TEST_DATABASE_URL` реальные SQL-тесты пропускаются. Старые FAQ-наборы проверяют исторический механизм на замороженных данных, рабочая Jana их не загружает. Скрипт `scripts/check_docker_stack.py` проверяет только созданный локальный Docker-стенд и оставляет явно помеченные тестовые заявки.
