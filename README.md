# PostTech — объединённый Digital HR

Сборочная ветка `codex/team-integration` объединяет backend `main`, портал и транзакционные процессы `test`, локальную Jana и экспорт календаря `Integration`. Изменения `ver2` проверены отдельно: параллельные старые SQL-триггеры не применяются, транзакции реализованы общими RPC. Общая Supabase этой сборкой не изменялась.

## Итоговый процесс

- Четыре роли: сотрудник, руководитель, директор, HR. Роль проверяет сервер.
- Заявка: `pending → pending_hr → approved/rejected`. Руководитель/директор выполняет первый этап, HR — окончательный; без руководителя заявка направляется HR сразу.
- Отпуск резервирует календарные дни включительно. Ожидание HR сохраняет резерв; окончательное одобрение списывает кадровый остаток один раз и закрывает резерв. Отмена своей ожидающей заявки освобождает резерв.
- Academy: назначенные уроки, проходной балл, повторные попытки и уведомления.
- Jana использует бесплатную локальную модель, опубликованные актуальные статьи и проверяемые цитаты. Вопросы не отправляются в облачный LLM. Качество понимания не гарантируется одной проверкой источника.
- Одобренный отпуск экспортируется в `.ics` для ручного импорта в Google Calendar. Автоматической синхронизации нет.

## Запуск локального демо без общей Supabase

Нужны Python 3.12 и Node.js. В корне новой копии:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe scripts/prepare_jana_reader.py
.\scripts\start_jana_reader.ps1
.\.venv\Scripts\python.exe -m uvicorn examples.jana_local_demo:app --host 127.0.0.1 --port 8002
```

Загрузка модели выполняется один раз, файл около 6,2 ГБ. Локальный reader слушает `127.0.0.1:8081`. Если он уже запущен, второй запуск не требуется. В другом терминале:

```powershell
cd frontend
npm ci
$env:VITE_DEMO_JANA_PROXY='/jana-demo'
npm run dev
```

Откройте адрес Vite, выберите демо-режим. Профили и заявки в этом режиме вымышленные и хранятся в памяти; вопросы Jana обрабатывает настоящий локальный reader через отдельный demo API. Ссылки открывают исходные статьи, календарь создаётся локально. Без demo API интерфейс явно сообщает, что Jana недоступна.

## Проверки на отдельном PostgreSQL

Нужна новая локальная PostgreSQL БД с именем `posttech_test_*`, без данных команды. Поддерживаются только loopback-адреса. Полный порядок миграций указан в `database/migration-plan.json`; запуск всех SQL файлов по алфавиту запрещён, ветки имели разные цепочки миграций.

```powershell
.\.venv\Scripts\python.exe -m pip install -r tests/requirements-db.txt
$env:POSTTECH_TEST_DATABASE_URL='postgresql://USER:PASSWORD@127.0.0.1:5432/posttech_test_local'
.\.venv\Scripts\python.exe -m pytest -q
cd frontend
npm test
npm run build
npm run test:e2e
```

DB-тесты создают отдельные одноразовые базы. HTTP+SQL проверки подменяют только внешнюю Auth-идентификацию и транспорт Supabase; транзакции, роли БД, права, резервы и списание выполняются настоящим PostgreSQL. Это не проверка реального Supabase Auth.

`scripts/export_jana_demo.py` только генерирует `database/seed_jana_demo.sql`; этот seed допускает применение исключительно к `posttech_test_*`. Он содержит 13 вымышленных статей с датами проверки. Старые FAQ и отчёты относятся к прежним версиям и не определяют поведение текущей Jana.

## Подключение настоящего проекта

Перед подключением Supabase необходимо отдельно сверить применённые миграции проекта и подготовить план перехода. **Не применять bootstrap-план новой БД к существующей общей базе.** После согласования настроить приватный `.env`, запустить reader и API `uvicorn app.main:app --host 127.0.0.1 --port 8000`, а frontend подключить через его `/api/v1` proxy.

Docker сохраняет сборку портала/API и опциональный integrations worker. Запуск локальной модели внутри Docker здесь не настроен: для Jana используйте описанный выше native запуск. 1С/Documentolog остаются отключёнными, пока отдельно не настроены и не проверены реальные принимающие системы.
